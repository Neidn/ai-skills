# 작성 규칙

## 문체

| 산출물 | 문체 | 예 |
|---|---|---|
| 포트폴리오·vault 프로젝트 파일 | 평서 선언형 "~한다" | "Redis로 OAuth 등록 상태를 레플리카 간 공유한다." |
| 이력서 bullet (국문) | 명사형 종결, 도메인 그룹 헤더 아래 | "NCP MCP 서버 단독 설계·구현 (OAuth2/OIDC, 3-replica K8s)" |
| 경력기술서 | 지원처 양식에 맞춤 ("~함" 또는 "~한다") | — |
| 자기소개서 | 경어체 "~습니다" | — |
| 영문 이력서 | 과거형 동사로 시작, 1줄 1성과 | "Designed and built an MCP server..." |

한 문서 안에서 문체를 섞지 않는다. 회사가 두 곳 이상이면 bullet 형식·길이를 맞춘다.

## 역할 동사 사다리

실제 기여에 맞는 가장 정확한 단계를 고른다. **한 단계라도 올려 쓰지 않는다.**

| 단계 | 국문 | 영문 | 쓰는 경우 |
|---|---|---|---|
| 5 | 단독 설계·구현 | Designed and built (solo) | 혼자 처음부터 만듦 |
| 4 | 주도 | Led | 팀 작업에서 방향·핵심 구현 담당 |
| 3 | 재작성·개선 | Rewrote / Improved | 인수한 코드를 크게 바꿈 (신규 아님) |
| 2 | 구현 담당 | Implemented (part) | 일부 모듈·계층만 담당 |
| 1 | 조율·사전 검증·기술 지원 | Coordinated / Validated / Supported | 실제 수행은 벤더·고객 |

## 수치와 근거

- 수치는 vault에 근거가 있을 때만 쓴다. 없으면 `[직접 입력 필요]`.
- 근거는 있으나 재확인이 필요하면 `[확인 필요]`.
- 코드 주석·커밋·로그에서 가져온 수치는 vault에는 출처를 괄호로 남긴다
  (예: "15개 터널 약 3~5초 (checker.py 주석 기준)"). 제출 문서에서는 괄호를 뺀다.
- Before → After 형태가 가장 강하다: "약 1일 → 10분".

## 금지 패턴

- 검증되지 않은 %·배수 ("성능 300% 향상")
- 기여 범위를 흐리는 과한 동사 ("쿠버네티스 업그레이드 수행" ← 조율만 했으면 금지)
- 학습·PoC·Lab을 운영 경험처럼 쓰기 (`status: lab/poc`면 "검증", "PoC"를 명시)
- 도구 나열만 있고 문제·결과가 없는 bullet
- 고객사 실명 (`disclosure: anonymize`)

## 문제 해결 사례 서술

`문제 → 원인 분석 → 해결` 3단. 원인 분석에 **왜 그런지(원리)**를 한 문장 넣는다.
면접에서 가장 많이 파고드는 부분이라, 원리 문장이 없으면 사례로서 약하다.
