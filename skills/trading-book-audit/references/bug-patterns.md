# 손익 회계 버그 카탈로그

실거래 시스템에서 반복적으로 관찰되는 네 가지. 공통점은 **조용하다**는 것 — 예외도
경고도 없이 그럴듯한 숫자를 오래 보고하고, 그 숫자를 읽는 다른 로직까지 같이 틀리게
만든다. 해당하는 항목만 읽는다.

---

## 1. 청산 사유 귀속 — 실행된 주문 타입으로 귀속

**증상**

- 청산 사유 분포에 손절이 0건이거나 극히 적다
- 거의 모든 청산이 하나의 기본값(`market_close` 등)으로 몰려 있다
- 출구 분석("손절이 너무 타이트한가")이 전부 무의미해진다

**원인**

조건부 주문(stop, take-profit)이 **발동되면** 거래소 체결 이벤트가 주문 타입 필드를
*실행된* 타입으로 덮어쓴다. 원래 타입은 별도 필드에 남는다. Binance Futures
`ORDER_TRADE_UPDATE`가 대표적이다.

| 필드 | 의미 | 발동된 STOP_MARKET의 값 |
|---|---|---|
| `o` | **현재/실행된** 주문 타입 | `MARKET` |
| `ot` | **원래** 주문 타입 | `STOP_MARKET` |

`o`로 사유를 매핑하면 발동된 손절이 전부 "시장가 청산"이 된다.

**수정**

원래 타입을 우선으로 읽고, 없는 페이로드만 실행된 타입으로 폴백한다.

```python
# 발동된 조건부 주문은 o가 실행 타입으로 바뀌어 도착한다.
# 원래 타입은 ot에 남아 있으므로 ot를 우선한다.
order_type: str = o.get("ot") or o.get("o", "")
```

**재현 테스트**

```python
def test_triggered_stop_maps_to_sl_hit():
    msg = fill_msg(order_type="MARKET", orig_type="STOP_MARKET", status="FILLED")
    listener.handle(msg)
    assert db.close_reason(symbol) == "sl_hit"   # 수정 전: "market_close"
```

**검증(실데이터)** — 손절 건수를 거래소 측 조건부 주문 이력과 대조한다. 로그만으로는
확인이 안 된다.

## 2. 부분청산 누적 — 최종 청산이 앞선 손익을 덮어씀

**증상**

- 사이징 오버레이(Kelly 등)가 최소치에 붙어 떠나지 않는다
- 승률·PF가 체감보다 나쁘고, 특히 "이겼던" 거래가 소액 손실로 남아 있다
- 편향이 **한 방향**이다 (항상 과소보고, 절대 과대보고 아님)

**원인**

TP1에서 절반을 확정해 손익을 기록한 뒤, 최종 청산에서 남은 수량의 손익을 계산해
**대입(=)** 한다. 앞서 확정한 이익이 사라진다. 손실 거래는 TP1에 닿지 않으므로 영향이
없다 → **손실은 정확하고 이익만 깎인다** → 기대값이 실제보다 나쁘게 보인다.

이것이 위험한 이유: 손익 컬럼을 읽는 **사이징 로직**이 그 왜곡된 값으로 켈리 비율을
계산해 스스로 최소치로 조인다. 리포트 버그가 아니라 **자본 배분 버그**다.

**수정**

남은 수량의 손익을 앞서 확정한 값에 **더한다.**

```python
prior_pnl = float(row["realized_pnl"] or 0)      # TP1에서 확정한 금액
leg_pnl = (exit_price - entry) * qty if side == "long" else (entry - exit_price) * qty
realized_pnl = prior_pnl + leg_pnl               # 대입(=)이 아니라 누적
```

**같은 버그가 여러 곳에 있다.** 청산 경로가 둘 이상이면(체결 리스너, 포지션 동기화
잡, 수동 청산) 전부 grep해서 같이 고친다. 한 곳만 고치면 경로에 따라 값이 달라진다.

**재현 테스트**

```python
def test_final_close_accumulates_tp1_profit():
    pos = open_position(entry=100, qty=2, side="long")
    partial_close(pos, exit_price=110, qty=1)      # +10 확정
    assert db.realized_pnl(pos) == 10
    mark_closed(pos, exit_price=105)               # 남은 1개 +5
    assert db.realized_pnl(pos) == 15              # 수정 전: 5
```

## 3. 죽은 리스크 가드 — 호출자가 없거나 빈 테이블을 읽음

**증상**

- 손실 한도를 넘겼는데 아무것도 차단되지 않았다
- 문서·docstring은 보호된다고 주장한다
- 그 함수의 테스트는 통과한다

**원인 (두 가지가 겹친다)**

1. **호출자가 0개다.** 함수는 존재하고 테스트도 있지만 실행 경로에서 아무도 부르지 않는다.
2. **아무것도 채우지 않는 테이블을 읽는다.** 합계가 항상 0 → 항상 "한도 미달" 반환.

**항상 False를 반환하는 가드는 가드가 없는 것보다 나쁘다.** 문서가 보호를 약속하기
때문에 아무도 다시 보지 않는다.

**테스트가 거짓 안심을 준 이유**

```python
# ❌ 실전에서 올 수 없는 입력을 주입해 죽은 가드를 "정상"으로 증명한다
def test_daily_limit():
    db.insert("daily_performance", date=today, net_pnl=-500)   # 아무도 이 행을 안 만든다
    assert guard.is_daily_limit_reached() is True
```

**실전에서 그 입력이 어떻게 만들어지는지**를 테스트가 보여주지 못하면, 그 테스트는
함수의 산수만 검증하고 배선은 검증하지 않는다.

**수정 절차**

```bash
grep -rn "is_daily_limit_reached" src/ | grep -v test   # 호출자 확인이 먼저
```

- 호출자가 없으면 → 삭제하거나 `# NOT WIRED`로 명시. 애매하게 남기지 않는다.
- 배선한다면 → **원천 데이터에서 직접 재계산**한다. 집계 테이블을 경유하지 않으면
  집계 잡이 죽어도 가드는 산다.
- 배포 전에 **실제 DB에** 쿼리를 한 번 돌려본다. 조용한 쿼리 실패가 원래 사인이었다.
- 가드가 무엇을 하는지 정확히 쓴다. "신규 진입 차단"과 "포지션 청산"은 다른 기능이다.

## 4. 집계 테이블이 계속 비어 있음

**증상**

- 일일 리포트가 "거래 없음"으로 나온다. 실제로는 거래가 있었다
- 집계 테이블을 읽는 모든 것(리포트, 명령어, 가드)이 0을 본다

**원인 (독립적인 두 개가 동시에 성립할 수 있다)**

1. **아무도 롤업을 호출하지 않는다.** 함수가 어떤 모듈의 `main()`에 있는데, 스케줄러는
   다른 모듈을 실행한다.
2. **호출돼도 틀린 날짜를 집계한다.** `CURRENT_DATE`로 하드코딩된 롤업이 00:00 UTC에
   돌면 *막 시작한* 날을 집계한다 → 0행 → early return → 아무것도 안 씀.

**수정**

- 기본값을 **어제**로 한다. 오늘을 집계하려면 명시적 인자로 받는다.
- 롤업을 **유일한 소비자 옆에서** 호출한다(일일 리포트 잡 안). 별도 스케줄 엔트리는
  또 끊긴다.
- 과거 구간은 백필 함수를 따로 만든다. **백필 값은 당시 버그를 물려받는다** — 원장과
  어긋나면 원장이 맞다. 리포트 연속성 용도로만 쓰고 그렇게 라벨링한다.

```python
def roll_up(conn, target_date: str | None = None) -> None:
    if target_date is None:
        # 이 잡은 자정 직후에 돈다. "오늘"은 막 시작한 날이라 0행이다.
        target_date = (datetime.now(timezone.utc).date() - timedelta(days=1)).isoformat()
```

**왜 오래 안 잡혔나** — 롤업 쿼리에 파라미터 쪽 캐스트(`%s::date`)가 있으면 sqlite
기반 테스트에서 깨져서 테스트가 아예 작성되지 않는다. `queries.md`의 타입 함정 참고.

---

## 공통 교훈

1. **필드의 소비자를 감사한다. 리포터만 보지 않는다.** "이 컬럼은 못 믿는다"고 몇 달간
   알려져 있어도, 그 컬럼으로 주문 수량을 정하는 코드는 아무도 확인하지 않는다.
2. **기능이 존재한다고 믿기 전에 호출자를 grep한다.** docstring과 테스트 둘 다 거짓일
   수 있다.
3. **테스트가 실전에서 불가능한 입력을 만들고 있는지 본다.** 주입된 fixture가 배선
   부재를 가린다.
4. **배포 전에 새 쿼리를 실제 DB에 돌린다.** 조용한 쿼리 실패로 기능이 죽는다.
5. **편향의 방향을 확인한다.** 한 방향 편향(항상 과소/과대)은 버그의 강한 신호다.
   진짜 노이즈는 양방향이다.
