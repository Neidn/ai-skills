# 유형별 골격

각 골격은 **출발점**이다. 이 문서에 없는 섹션은 빼고, 필요한 건 더한다. 대괄호 `[ ]`는
그 섹션에 무엇을 쓰는지 메모다 — 개요 단계에서 제목 아래 이 한 줄을 남겨두면 좋다.

---

## 보고서

의사결정자용이면 요약을 맨 앞에 둔다(바쁜 사람은 요약만 읽는다).

```
1. 요약            [핵심 결론·수치 3~5줄. 이것만 읽어도 되게]
2. 배경·목적       [왜 이 보고를 하는가, 무엇을 다루는가]
3. 현황·분석       [사실과 데이터. 본론]
4. 결론·제언       [그래서 무엇을 하자는가. 실행 항목]
부록               [상세 데이터·근거자료]
```

- 요약은 마지막에 쓴다(본문이 끝나야 요약할 수 있다). 위치만 앞일 뿐이다.
- "분석"과 "결론"을 섞지 않는다 — 사실은 3에, 판단은 4에.

## 매뉴얼 · 절차서

MSP 운영 문서의 기본. `document-design`·운영 규칙(AGENTS.md)의 "롤백" 원칙과 짝을 이룬다.

```
1. 목적·범위       [이 문서로 무엇을 할 수 있나 / 다루지 않는 것은 무엇인가]
2. 사전조건        [권한, 접근 경로, 필요한 정보·도구. 없으면 시작도 못 하는 것들]
3. 절차            [번호 매긴 단계. 한 단계 = 한 동작]
   3.1 …
4. 검증            [끝났는지 어떻게 아는가. 성공 판정 기준]
5. 롤백·문제해결   [잘못됐을 때 되돌리는 법 / 자주 나는 오류와 대처]
```

- **범위의 "제외" 항목을 꼭 쓴다.** 안 하는 것을 명시해야 범위 다툼이 없다.
- 각 단계에 "이렇게 되면 정상" 확인 포인트를 넣는다.
- 되돌리기 번거로운 단계엔 주의 콜아웃(→ document-design)을 단다.

## 제안서

```
1. 배경·문제 인식  [고객이 겪는 문제. 고객 언어로]
2. 목표            [이 사업으로 도달할 상태. 측정 가능하게]
3. 수행 방안       [무엇을 어떻게. 범위와 산출물]
4. 추진 일정       [단계·마일스톤]
5. 소요 비용·자원  [견적. 범위와 연결]
6. 기대효과        [끝나면 무엇이 좋아지나]
7. 지원 범위·경계  [무엇을 해주고 어디부터 고객/타사 책임인가]
```

- 7번(범위·경계)이 실무에서 가장 중요하다. 지원 vs 대행, 초기 vs 지속, 인프라 vs 앱을
  구분해 적는다. 견적서라면 이 경계가 곧 금액 방어선이다.

## 장애 보고서

```
1. 요약            [무슨 장애가, 언제, 얼마나. 3줄]
2. 타임라인        [탐지→대응→복구 시각별. 사실만]
3. 영향            [어떤 서비스·고객이, 얼마 동안]
4. 원인            [직접 원인 + 근본 원인 구분]
5. 조치            [당시 취한 조치 / 복구 방법]
6. 재발 방지       [무엇을 바꿀 것인가. 담당·기한 포함]
```

- 타임라인은 **사실과 시각만**. 추정·판단은 4·6에.
- 원인에서 개인 책임을 묻지 않는다(비난 없는 회고). 시스템·프로세스로 쓴다.
- 재발 방지는 "노력하겠다"가 아니라 담당자·기한이 붙은 실행 항목으로.

## 인수인계 문서

```
1. 개요            [무슨 시스템·업무인가. 한눈 요약]
2. 시스템 구성     [아키텍처·리소스 목록. 구성도 첨부(→ cloud-architecture-diagram)]
3. 운영 절차       [정기 작업, 배포, 백업, 모니터링]
4. 계정·접근       [어디에 어떻게 접근하나. 실제 자격증명은 문서에 넣지 않음]
5. 알아둘 것       [함정, 미해결 이슈, 임시방편, 과거 장애 이력]
6. 연락처          [벤더·고객·유관부서. 이름·역할·연락 방법]
```

- 4번에 **비밀번호·키를 직접 쓰지 않는다.** "어디(금고/볼트)에 있다"만 적는다.
- 5번이 인수인계의 진짜 가치다. 문서엔 안 나오는 "이건 건드리면 터진다"를 남긴다.

## 기술 검토서 (비교·선정)

```
1. 배경·목적       [무엇을 결정하려는가]
2. 후보            [비교 대상. 왜 이것들을 골랐나]
3. 평가 기준       [무엇으로 비교하나. 가중치. 결론보다 먼저 정한다]
4. 비교·평가       [기준별 표. 근거]
5. 결론·권고       [무엇을 고르나, 왜. 트레이드오프도 명시]
부록               [상세 벤치마크·근거]
```

- **기준(3)을 결론(5)보다 먼저 확정한다.** 결론에 맞춰 기준을 짜맞추면 검토가 아니라 정당화다.
- 탈락한 후보도 "왜 아닌지"를 남긴다. 나중에 같은 논의를 반복하지 않게.

---

## 공통 조정 원칙

- 짧은 문서(2~3쪽)는 섹션을 합친다. 골격을 다 채우려 하지 않는다.
- 긴 문서(20쪽+)는 섹션을 문서로 분리하고 상위에 개요 문서를 둔다.
- 어느 유형이든 **요약을 앞, 근거를 뒤, 상세를 부록**으로 두면 대체로 옳다.
