# Kubernetes Operations

kubectl로 클러스터를 직접 운영하되, **조회는 자동 실행, 상태를 바꾸거나 민감정보를
노출하는 작업은 승인한 범위 안에서만, 되돌릴 수 없는 작업은 하지 않는다**가 핵심
원칙이다. 대상은 kubectl로 접근 가능한 모든 클러스터이며, 특정 클라우드·모니터링·
자동화 도구에 의존하지 않는다. 그런 도구가 필요한 부분(kubeconfig 발급, 외부 LB
헬스, 감사 로그, 승인 채널)은 환경 프로필에 적힌 방법을 따른다.

## 0. 시작 전에 — 환경 프로필과 대상 클러스터 확인

1. **환경 프로필을 읽는다.** `K8S_OPS_PROFILE` → 작업 디렉터리의
   `k8s-ops-profile.yaml` 순으로 찾는다. 양식, 없을 때의 기본값, 값 찾는 방법은
   `references/environment-profile.md`에 있다. 프로필이 없어도 조회는 진행하되
   대상 환경은 prod로 간주한다.
2. **kubeconfig를 확인한다.** 프로필의 `kubeconfig.issue_command`로 임시 발급하는
   환경이면 작업 디렉터리에 발급해 `--kubeconfig`로 지정하고, 작업이 끝나면 지운다.
   kubeconfig 내용과 토큰은 출력하지 않는다. `--kubeconfig`, `--context`, `-n` 같은
   전역 플래그는 **동사 뒤에** 붙인다(`kubectl get pods -n a --kubeconfig ./kc`).
   권한 규칙이 `kubectl <동사>`로 시작하는 형태를 기준으로 매칭하기 때문이다.
3. **대상 클러스터를 확인한다.** `kubectl config current-context`로 지금 어느
   클러스터를 보고 있는지 확인하고, 사용자가 말한 대상·프로필의 `context`와
   일치하는지 확인한다. 네임스페이스도 `-n <namespace>`를 명시한다. **컨텍스트를
   잘못 짚고 실행하는 것이 이 작업에서 가장 흔하고 위험한 실수다** — 특히 여러
   클러스터(dev/staging/prod)를 다루는 환경에서는 매 요청마다 확인한다.
   실행 환경이 `kubectl config`를 막아 둔 경우(클러스터 1개 = 실행 환경 1개 구성
   등)에는 `kubectl cluster-info`의 API 서버 주소와 `kubectl get nodes` 결과를
   프로필과 대조해 확인한다.
4. **실행 경로의 제약을 확인한다.** 프로필 `executor.constraints`가 있으면(예: 중간
   실행 계층이 파이프·리다이렉트를 막음) 명령을 그 제약에 맞게 나눠 보내고, 정렬·
   필터 같은 가공은 결과를 받은 뒤에 한다.
5. **권한을 확인한다.** 변경 전에는 `kubectl auth can-i <verb> <resource> -n <ns>`로
   권한이 있는지 본다. 없으면 필요한 권한을 안내하고, 권한을 직접 바꾸지 않는다.

## 1. 명령 분류 — 조회 vs 승인 필요

전체 분류표는 `references/command-classification.md`에 있다. 요약하면:

| 분류 | 처리 | 예시 |
|---|---|---|
| **조회** | 바로 실행 | `get`, `describe`, `logs`, `top`, `explain`, `api-resources`, `version`, `cluster-info`, `events`, `diff`, `auth can-i`, `rollout status/history` |
| **승인 필요** | 실행 전 확인 | `apply`, `create`, `delete`, `patch`, `edit`, `replace`, `scale`, `autoscale`, `set`, `label`, `annotate`, `cordon`, `uncordon`, `drain`, `taint`, `exec`, `cp`, `rollout restart/undo/pause/resume` |
| **승인 필요 (민감정보)** | 실행 전 확인 | `get secret -o yaml\|json` 등 Secret 값이 디코딩되어 노출되는 조회 |
| **승인 필요 (파괴적)** | 실행 전 확인, 근거 요구 | `delete --force`, `--grace-period=0`, `evict` |
| **승인해도 실행 안 함** | 사용자가 직접 하도록 안내 | Namespace·PVC·PV·CRD·StorageClass 삭제, 셀렉터·`--all`·디렉터리 단위 일괄 삭제, RBAC 변경, 클러스터·노드·애드온 버전 변경 (아래 3번) |

Helm도 같은 기준이다. `list`·`status`·`history`는 조회, `get values`·`get manifest`는
민감정보, `upgrade`·`install`·`rollback`은 승인 필요, `uninstall`과 클러스터 구성요소
릴리스의 `upgrade`는 승인해도 실행 안 함. 상세는 분류표의 "Helm" 절에 있다.

애매한 명령(`kubectl apply --dry-run=client/server`, `port-forward` 등)은
`references/command-classification.md`의 "애매한 케이스"를 본다.

## 2. 승인 워크플로

"승인 필요"로 분류된 명령은 절대 먼저 실행하고 나중에 알리지 않는다. 실행 전에
아래 **조치계획**을 제시하고 명시적 승인을 받는다.

### 조치계획 양식

| 항목 | 내용 |
|---|---|
| 조치 코드 | 아래 표에서 고른다 |
| 대상 | 컨텍스트, 네임스페이스, 리소스 종류/이름. 생략하지 않는다 |
| 명령 | 실행할 명령 전문을 순서대로. 축약하지 않는다. 실행 경로에 제약이 있으면 1단계 = 1요청 = 명령 1개로 적는다 |
| 미리보기 | 가능하면 `--dry-run=server`나 `kubectl diff` 결과. `kubectl diff`는 차이가 있으면 종료 코드 1, 없으면 0이고 오류일 때만 1보다 크다 |
| 사전 확인 | 실행 직전에 다시 볼 상태와, 이미 복구됐으면 실행하지 않는다는 조건 |
| 영향 범위 | 영향받는 파드·리소스 수, 다운타임 여부 |
| 롤백 | 되돌리는 방법(예: `rollout undo`, 변경 전 `get -o yaml` 백업) |
| 재검증 | 서비스 기준 확인 항목. 프로필 `services[].required_components`를 **모두** 포함 |

| 조치 코드 | 내용 |
|---|---|
| `k8s_scale` | 이름을 명시한 워크로드 1개의 replicas 변경 |
| `k8s_rollout_restart` / `k8s_rollout_undo` | 이름을 명시한 워크로드 1개의 롤아웃 재시작·되돌리기 |
| `k8s_pod_delete` | 이름을 명시한 파드 삭제(컨트롤러가 다시 만드는 파드만) |
| `k8s_node_cordon` / `k8s_node_drain` | 이름을 명시한 노드 1대의 스케줄링 차단·축출 |
| `k8s_patch` | 이름을 명시한 리소스 1개의 명시한 필드만 변경 |
| `k8s_apply` | 매니페스트 적용. diff 결과를 계획에 첨부 |
| `pvc_expand` | 이름을 명시한 PVC 1개 용량 확장. StorageClass의 `allowVolumeExpansion` 확인 필수, 축소는 불가 |
| `helm_upgrade` / `helm_rollback` | 이름을 명시한 애플리케이션 릴리스 1개의 업그레이드·되돌리기. 차트 버전과 바뀌는 values를 계획에 적는다 |
| `custom` | 위에 없는 조치. 명령 전체를 계획에 적는다 |
| `none` | 조치 없이 기록만 |

### 승인 규칙

- **승인자와 경로**: 프로필 `approval.approver`가 `approval.channel`로 승인한 것만
  인정한다. 프로필이 없으면 이 대화의 사용자가 명시적으로 승인한 것만 인정한다.
  지정된 경로가 아닌 곳(다른 채팅방, 이슈 코멘트 등)의 "진행해"는 승인이 아니다.
  토큰 방식이면 토큰 일치, 1회용(미사용), 만료 전을 모두 확인한다.
- **승인 범위**: 승인한 것은 조치계획에 적은 명령·대상·순서뿐이다. 다른 명령, 다른
  대상, 순서 변경은 새 승인이 필요하다.
- **변경 단위별로** 받는다. 서로 다른 변경을 하나로 뭉쳐 한 번에 승인받지 않는다.
- 조치가 필요하고 금지 작업(아래 3번)이 아니면 "담당자 확인 필요"로 끝내지 말고
  조치계획을 만들어 승인을 요청한다.

### 실행과 판정

1. 실행 직전에 대상 상태를 다시 확인한다. 이미 복구됐거나 계획과 상태가 다르면
   멈추고 보고한다.
2. 승인받은 명령만 순서대로 실행한다. 권한 오류(Forbidden)가 나면 바로 멈추고
   필요한 권한을 안내한다.
3. 명령별 성공·실패와 출력 요약을 기록한다.
4. 재검증 항목을 조회로 확인한다. **재검증 근거가 있을 때만 "복구"로 보고**하고,
   없으면 장애 상태로 보고한다.

이 저장소(ai-skills) 기준으로는 `.claude/settings.json`에 "승인 필요" 명령은
`ask`로, "승인해도 실행 안 함" 명령은 `deny`로 거는 권한 규칙도 있어 이중 안전장치가
있다. **단, 이 규칙은 이 저장소에서 Claude Code를 쓸 때만 적용되고, 명령 문자열을
매칭할 뿐이라 다른 형태(`sh -c`, 매니페스트 안의 RBAC 리소스 등)로 쓰면 걸리지
않는다.** 이 스킬만 다른 프로젝트에 설치하면 도구 권한 강제도 없다. 그러니 도구
권한 설정 유무와 무관하게 이 워크플로를 항상 따른다. 실제 경계는 클러스터 쪽
권한(ServiceAccount RBAC)으로 잡는다.

## 3. 승인을 받아도 하지 않는 작업

되돌릴 수 없거나 영향 범위를 통제할 수 없는 작업은 승인을 받아도 실행하지 않는다.
요청을 받으면 거절 사유와 함께 사용자가 직접 작업하도록 안내하고, 필요해 보여도
조치계획에 넣지 않는다.

| 분류 | 작업 |
|---|---|
| 데이터 | Namespace·PVC·PV 삭제, 데이터베이스 데이터 삭제, 컨테이너 안 디렉터리·와일드카드 통삭제 |
| 클러스터 범위 | CRD·StorageClass·Node 오브젝트 삭제, 클러스터·노드풀 삭제(플랫폼 작업) |
| 일괄 삭제 | 라벨 셀렉터(`-l`)·`--all`·디렉터리(`-f <dir>`) 단위 삭제 |
| 권한 | Role·ClusterRole·RoleBinding·ClusterRoleBinding 생성·변경·삭제, `auth reconcile`, 플랫폼의 클러스터 접근 권한 변경 |
| 업그레이드 | 클러스터·노드 버전, 클러스터 구성요소(CNI·CSI·Ingress 컨트롤러 등) 버전 변경 |
| 보호 해제 | 삭제 보호·PDB 등 보호 장치를 우회하기 위한 해제 |

프로필 `approval.extra_forbidden`에 있는 작업도 같은 등급으로 취급한다.

## 4. 하지 말 것

- **승인 없이 "승인 필요" 명령을 실행하지 않는다.** 도구 권한이 자동 허용되어
  있어도 마찬가지다 — 이 스킬의 워크플로가 우선한다.
- `--force`, `--grace-period=0` 같은 강제 옵션을 사용자 확인 없이 쓰지 않는다.
- Secret 값을 채팅·파일·보고서에 그대로 남기지 않는다. 꼭 필요한 키만, 필요하면
  마스킹해서 보여준다. 프로필과 계획에는 비밀정보를 **환경변수 이름**으로만 적는다.
- 컨텍스트 확인 없이 "일단 실행해보고" 대상을 짐작하지 않는다.
- 여러 리소스를 한 번에 수정하는 명령(라벨 셀렉터 기반 `label -l ...` 등)은
  영향받는 리소스 목록을 먼저 `get`으로 보여준 뒤 승인받는다. 일괄 삭제는 3번에
  따라 하지 않는다.
- 노드 재기동·교체, 클라우드 리소스 변경처럼 kubectl 밖의 작업은 이 스킬에서
  실행하지 않는다. 필요하면 근거와 함께 사용자에게 안내한다.

## 5. 장애 조사

알람이나 장애 보고를 받으면 `references/incident-investigation.md`를 읽고 따른다.
요약하면:

- 조회 명령만으로 조사하고, 근거를 남기고, 확인 못 한 것은 "미확인"으로 적는다.
- 대상(컨텍스트/네임스페이스/리소스)을 먼저 확정하고 조사가 끝날 때까지 바꾸지 않는다.
- 이름·숫자로 추정하지 않고 실제 적용된 스펙·로그로 확인한다.
- 누가 바꿨는지는 이벤트, `rollout history`, `managedFields`, 플랫폼 감사 로그로 대조한다.
- 복구됐다고 바로 종결하지 않고 사후 분석과 재확인을 한다.
- 보고는 원인 → 근거 표 → 해결 방안 → 재발 방지 → 미확인 항목 순서로 쓴다.

## 6. 검수

**변경 작업 후**

- [ ] 실행한 명령이 승인받은 내용과 정확히 일치하는가
- [ ] 변경이 반영됐는지 조회 명령으로 재확인했는가
- [ ] `required_components`를 포함한 재검증 근거가 있는가 (없으면 "복구" 아님)
- [ ] 의도치 않은 다른 리소스에 영향이 없는가
- [ ] 롤백이 필요해질 경우의 방법을 사용자에게 남겼는가
- [ ] 임시 kubeconfig를 지웠는가

**보고·발송 전**

- [ ] 오타를 한 번 더 확인했는가. 코드·페이로드에 넣은 한글 문자열은 음절이 깨지기
      쉬우니 다시 읽어 대조한다
- [ ] 외부 채널(`platform_hooks.notify`)로 나가는 산출물은 생성된 내용을 먼저
      확인했는가. 운영 채널을 테스트 대상으로 쓰지 않는다
- [ ] Secret 값, 토큰, 실제 공인 IP가 들어가지 않았는가
- [ ] 오타를 발견해 고쳤으면 사과문 없이 수정 사실과 근거만 짧게 알린다
