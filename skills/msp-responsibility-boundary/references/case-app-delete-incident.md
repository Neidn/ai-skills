# 적용 예시: 애플리케이션 쿼리 오류로 인한 데이터 삭제

이 스킬의 판단 기준을 하나의 가상 시나리오에 적용한 예시다. 특정 고객·제품·사건과
무관하게 일반화했다.

## 시나리오

- 고객사 업무 시스템: WAS + 상용 DBMS 구성, 인프라는 MSP가 운영
- 애플리케이션의 DELETE 쿼리 조건 오류로 업무 테이블 데이터가 대량 삭제됨
- 인프라 모니터링은 정상 (가용성 체크는 로그인 전 응답 코드만 확인)
- 개발사는 로그 분석 없이 DBMS 제조사 기술지원을 고객사를 통해 요청 — 실질은 DBA 지원 요구
- 인프라 엔지니어는 장애 대응 중 앱 로그를 확인해 원인 쿼리를 이미 짐작하고 있음
- 대응이 지연되자, 확인한 내용을 고객사 참조 메일로 보내 개발사를 압박하고 싶어짐

## 판단 흐름

| 질문 | 판단 | 근거 |
|---|---|---|
| 원인 계층? | 애플리케이션 | 엔진은 받은 DELETE를 정상 수행 |
| 제조사 지원이 맞나? | 아니오 | 제품 결함 아님, DBA 성격 요구 |
| 확인한 내용 전달? | 0단계 보관 | 앱 로그 분석은 범위 밖, 접근 근거 없음, 업무 데이터 포함 가능 |
| "모니터링 중 확인"이라고 쓸까? | 아니오 | 모니터링은 정상이었음 — 사실과 다름 |
| 인프라 재발 방지 대책? | 넣지 않음 | 원인이 앱 로직. 넣으면 책임 일부 인정으로 읽힘 |
| 데이터 변동 감시 제안? | 아니오 | DB 안 데이터를 보는 것 = 앱 영역 |
| 압박용 로그 캡처? | 아니오 | 범위 논리 붕괴, 민감 데이터 노출, 역공 빌미, 관계 비용 |
| 대신 무엇을? | 2~3단계 | 로그 위치 + 확인 방법 안내, 보고서 필수 항목 지정, 짧은 기한, 3자 회의 |
| 지연 사유? | 사실대로 | 제조사에 기술지원 가능 여부를 확인하는 중이었음 |

## 버틸 경우 대비

- "로그에 없다" → 확인 근거 요구 (파일 범위·조건·보존 여부), 별도 로그 출구
- 동일 조건 재확인 → 고객사 승인 후, `DELETE FROM 테이블명`까지만 잘라서 파일·라인·시각 회신
- 최후 → 3자 공동 확인 세션

## 교훈

빨리 끝내고 싶을 때 가장 강한 유혹은 "이미 찾은 걸 보여주는 것"이다. 효과는 즉각적이지만
그 순간 인프라가 앱 로그 분석 주체가 되고, 다음 장애부터 같은 요청이 온다. 속도는 압박이
아니라 **기한·필수 항목·3자 회의**라는 구조에서 나온다.
