# 정보 공개 사다리

인프라가 이미 알고 있는 것과, 공식적으로 건네도 되는 것은 다르다. 가장 낮은 단계에서
시작하고, 상대가 협조하지 않을 때만 한 칸씩 올린다.

## 접근 근거 먼저

공개 단계를 정하기 전에 그 정보를 어떻게 얻었는지 본다.

| 획득 경위 | 근거 | 기본 단계 |
|---|---|---|
| 계약된 모니터링·점검 | 있음 | 1 |
| 장애 접수 후 인프라 영역(엔진·자원) 점검 | 있음 | 1 |
| 장애 접수 후 범위 밖 영역(앱 로그·데이터) 확인 | **없음** | 0 |
| 고객사 승인 후 확인 | 있음 | 4까지 |

근거가 없는 정보를 공개해야 할 상황이면, 공개 전에 고객사 승인을 받아 **다시 확인하는
절차**를 만든다. 승인 없이 확인한 결과를 그대로 꺼내지 않는다.

## 단계

| 단계 | 전달 내용 | 예시 문구 |
|---|---|---|
| 0 | 없음. 내부 보관, 상대 보고서 대조용 | - |
| 1 | 인프라 관점 사실 | "장애 시점 DBMS 엔진은 정상 동작하였습니다" |
| 2 | 근거 위치 | "쿼리 이력은 앱 로그(catalina.out)에서 확인 가능할 것으로 보입니다" |
| 3 | 확인 방법 | "장애 시점 전후 DELETE 구문을 검색하는 방식으로 확인 가능할 것으로 보입니다" + 명령 예시 |
| 4 | 존재 여부·위치 (고객사 승인 필요) | "{파일} {시각} 전후 구간에 해당 조건의 기록이 존재합니다" |
| 5 | 공동 확인 세션 (고객사 승인 필요) | 3자 참석, 인프라는 접근만 지원, 상대가 직접 조작 |

## 단계별 주의

- 2~3단계는 "확인해 보니 있더라"가 아니라 **"확인해 보시라"** 권고형으로 쓴다.
- 3단계 명령 예시에는 로테이션 파일까지 포함한다 (`zgrep` 등). 범위 누락 핑계를 막는다.
- 4단계 캡처는 **원인이 드러나는 부분 앞에서 자른다.** 예: `DELETE FROM 테이블명`까지,
  WHERE 절부터 제외. 세션 ID·IP·사용자 계정도 제외. 이미지를 가리기보다 출력 자체를
  잘라낸다:

  ```
  grep -noi "delete from [a-z0-9_.]*" catalina.out
  sed -n '{라인}p' catalina.out | cut -c1-{시각 길이}
  ```

- 5단계에서 기록이 나오면 누구도 반박할 수 없고, 인프라의 접근도 승인 근거를 갖는다.
  0단계에 숨겨둔 내용을 드러낼 필요도 없어진다.

## 에스컬레이션: 상대가 "없다"고 할 때

1. **확인 근거 요구** — 확인한 파일 범위(로테이션 포함), 검색 조건, 로그 보존 여부를 회신
   받는다. 별도 경로 로그도 확인하라는 문장으로 출구를 열어둔다. 대부분 여기서 끝난다.
2. **유실 주장** — 보존을 이미 요청했다면 유실은 상대 관리 책임이다. 코드 기반 전수
   점검(해당 객체에 접근하는 코드·프로시저 전부)으로 분석 대체를 요구한다.
3. **동일 조건 재확인** — 고객사 승인 후 상대가 준 조건 그대로 재검색. 결과가 다르면
   4단계 수준으로만 회신하고, 차이 원인을 **방법의 차이**(파일 범위·시간대)로 설명한다.
   "못 찾았다"가 아니라 "범위를 놓쳤다"로 받아들일 수 있게 한다.
4. **공동 확인** — 그래도 버티면 5단계.

로그 유실 위험이 있으면 1단계 회신을 기다리기 전에 고객사에 원본 보존을 다시 요청한다.
