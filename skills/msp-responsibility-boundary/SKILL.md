# MSP Responsibility Boundary

**원인이 있는 계층의 주체가 분석과 재발 방지를 책임진다.** 인프라가 더 잘 알고, 더 빨리
찾을 수 있어도 마찬가지다. 범위 밖 일을 한 번 해주면 그게 다음 장애의 기본값이 되고,
결과가 틀렸을 때의 책임까지 넘어온다.

두 번째 원칙: **선을 긋는 것은 "안 됩니다"가 아니라 구조로 한다.** 범위를 문서로
정리해서 고객사가 판단하게 만들면, 인프라가 거절하지 않아도 결론이 난다.

세 번째 원칙: **아는 것과 건네는 것은 다르다.** 확인한 내용은 판단의 근거로 쓰되,
전달은 접근 근거와 범위가 허락하는 수준까지만 한다.

## 워크플로

### 1. 원인 계층 판정

장애나 요청이 어느 계층에서 생겼는지 먼저 정한다. 판정 기준표는
`references/layer-matrix.md`를 읽는다. 요약:

| 계층 | 예시 | 주체 |
|---|---|---|
| 인프라 | 서버·네트워크·스토리지·OS 가용성, 방화벽, 백업 수행 | MSP |
| 미들웨어/엔진 | DBMS·WAS 엔진 가동 여부, 엔진 로그 | MSP (가용성까지) |
| 애플리케이션 | 쿼리 로직, 프로시저, 앱 로그, 계정 권한 설계 | 개발사 |
| 데이터 | 데이터 정합성·변동, 업무 데이터 내용 | 개발사 / 고객사 |
| 제품 결함 | DBMS·OS·장비 자체 버그 | 제조사 |

판정이 애매하면 **"엔진/플랫폼은 명령대로 동작했는가"**를 묻는다. 그렇다면 원인은 그
명령을 보낸 쪽이다.

### 2. 요청된 지원이 맞는 종류인지 확인

상대가 요구하는 지원 형태가 원인 계층과 맞는지 본다. 자주 생기는 어긋남:

- **제조사 기술지원 ≠ DBA 서비스.** 제조사 기술지원은 제품 결함·장애·패치 대상이다.
  쿼리 분석·데이터 검증은 DBA 성격이며 보통 별도 유상 계약이다.
- **인프라 운영 ≠ 앱 로그 분석.** 앱 로그 위치 안내는 협조, 분석은 범위 밖이다.
- **가용성 모니터링 ≠ 정합성 감시.** 응답 코드·엔진 상태는 인프라, 데이터 변동 감지는
  애플리케이션 영역이다. DB 안의 데이터 변동을 인프라가 감시하는 건 "데이터를 들여다본다"는
  의미가 되므로 제안하지 않는다.

어긋남을 지적할 때는 가능하면 **제3자(제조사 엔지니어 등)의 확인을 근거로** 쓴다.
인프라가 직접 거절하는 것보다 훨씬 깔끔하다. 구두 확인이면 한 줄이라도 서면으로 받아둔다.

### 3. 정보 공개 수준 결정

`references/disclosure-ladder.md`의 사다리에서 현재 단계를 고른다. 기본은 가장 낮은
단계에서 시작하고, 상대가 협조하지 않을 때만 한 칸씩 올린다.

0. 내부 보관 (대조용)
1. 인프라 관점 사실만 ("엔진은 정상 동작")
2. 근거가 있는 **위치** 안내 ("앱 로그에서 확인 가능할 것으로 보임")
3. 확인 **방법** 안내 (명령어 예시)
4. 고객사 승인 하에 **존재 여부·위치**만 회신 (파일·라인·시각, 내용 제외)
5. 고객사 승인 하에 3자 **공동 확인** 세션 (상대가 직접 조작)

어느 단계에서도 하지 않는 것: 원인 해석 전달, 개인정보가 담긴 원문·캡처 전달, 승인
없이 접근해 얻은 결과 공개, 상대를 망신 주는 방식의 압박.

**접근 근거를 먼저 따진다.** 확인 행위가 계약 범위(장애 대응·가용성 점검) 안이었는지
본다. 범위 밖에서 확인한 내용은 공개하는 순간 "누가 왜 봤나"가 쟁점이 되므로 0단계로
둔다. 공개 단계를 올려야 하면 그 전에 고객사 승인을 받아 근거를 만든다.

### 4. 재발 방지 대책 배정

원인 계층의 주체에게만 대책을 배정한다. **인프라가 원인이 아닌 장애에 인프라 대책을
끼워 넣지 않는다.** 선의라도 "인프라도 일부 책임이 있다"로 읽힌다.

상대에게 요구할 때는 대책 내용이 아니라 **보고서 필수 항목**을 지정한다. 항목이
구체적일수록 제대로 분석하지 않고는 답할 수 없다. 예: 수행 시각·수행 쿼리, 호출 경로,
오류 원인·영향 범위, 대책·적용 일정.

### 5. 대외 회신 작성

`references/reply-patterns.md`의 구조와 문구를 쓴다. 원칙:

- 고객사를 참조에 넣는다. 고객사가 R&R의 최종 판단자이자 압박의 주체가 된다.
- 순서: 인프라 점검 결과(사실) → 요청 지원의 범위 검토 → 원인 분석 요청 → 재발 방지
  요청 → 회신 기한·3자 회의 제안.
- 지연이 있었다면 **사실대로** 사유를 쓴다 (예: 제조사 기술지원 가능 여부 확인 중이었음).
- 모니터링으로 탐지하지 못한 사실은 숨기지 않고, 계약된 모니터링 범위로 설명한다.
- 상대가 체면을 지키며 물러설 **출구**를 하나 열어둔다 ("별도 경로 로그도 함께 확인 바람").
- 빨리 끝내려면 압박 대신 짧은 회신 기한과 3자 회의 제안을 쓴다.

### 6. 상대가 버틸 때

"로그가 없다", "확인이 안 된다"는 회신이 오면 `references/disclosure-ladder.md`의
에스컬레이션 절을 따른다: 확인 근거 요구 → 유실이면 코드 기반 분석으로 대체 요구 →
고객사 승인 하 존재 여부 회신 → 3자 공동 확인.

## 검수

- [ ] 원인 계층과 책임 주체를 명시했는가
- [ ] 요청된 지원 형태가 계층과 맞는지 확인했는가 (제조사 지원 ≠ DBA 등)
- [ ] 전달하는 정보가 접근 근거와 공개 단계에 맞는가
- [ ] 개인정보·원인 해석이 회신·캡처에 들어가지 않았는가
- [ ] 인프라가 원인이 아닌데 인프라 대책을 넣지 않았는가
- [ ] 고객사가 참조되어 있고, 회신 기한이 있는가
- [ ] **추측과 확인된 사실을 구분해서 썼는가** (특히 제3자 답변 인용 시)

## 하지 말 것

- 범위 밖 분석을 대신 해주고 결과를 건네지 않는다. 빨리 끝내고 싶을 때 가장 흔한 실수다.
- 범위 밖에서 확인한 내용으로 상대를 공개적으로 압박하지 않는다. 범위 논리가 스스로 무너지고,
  접근 근거가 역공의 빌미가 된다.
- 범위를 넓히는 재발 방지 제안(로그인 후 모니터링, DB 데이터 변동 감시 등)을 인프라
  대책으로 내지 않는다.
- 사실과 다른 탐지 경위를 쓰지 않는다 ("모니터링 중 확인" 등). 나중에 "왜 늦었냐"로 돌아온다.
- 제3자(제조사 등)의 답변을 실제보다 강하게 인용하지 않는다. 애매했으면 "판단됩니다"로 쓴다.
