# 주식 손익 회계 버그 카탈로그

국내주식 자동매매에서 반복되는 여섯 가지. 공통점은 **조용하다**는 것이다. 예외도
경고도 없이 그럴듯한 숫자를 오래 보고하고, 그 숫자를 읽는 다른 로직까지 같이 틀리게
만든다. 해당하는 항목만 읽는다. 코인 공통 패턴(청산 사유 귀속, 부분청산 덮어쓰기)은
`trading-book-audit/references/bug-patterns.md`에 있다. 주식에서도 TP1 분할매도 후
최종 매도가 앞선 손익을 **대입(=)** 하는 버그는 그대로 나타난다.

## 1. 기업행위 미반영 — 분할·무상증자·배당락

**증상**

- 특정 종목 하루 손익이 −50%, −80% 같은 비현실적인 값이다
- 거래정지가 풀린 날 아침, 그 종목에 손절 주문이 나갔다
- 잔고 수량(증권사)과 로컬 수량이 정수배로 다르다
- 배당락일마다 보유 종목에서 작은 손실이 찍히고, 배당 입금은 어디에도 없다

**원인**

액면분할(1:N)이면 증권사 잔고는 수량 ×N, 평균단가 ÷N으로 바뀐다. 로컬 테이블은 옛
평균단가와 옛 수량을 들고 있다. 첫 시세가 들어오면 다음 일이 생긴다.

- 평가손익 = (새 가격 − 옛 평균단가) × 옛 수량 → 거대한 손실
- 가격 기반 손절 `price < entry * 0.95`가 **즉시 참** → 실제로는 멀쩡한 포지션을
  시장가로 판다
- 수량이 안 맞아서 매도 주문이 "잔고 부족"으로 거부되거나, 반대로 일부만 판다

무상증자·주식배당은 권리락으로 가격이 내려가고 신주는 며칠 뒤 입고된다. 배당락은
가격이 배당만큼 내려가고 현금은 수 주~수개월 뒤에 들어온다. **가격 하락과 보상이 서로
다른 날, 다른 테이블에 기록된다.**

**수정**

- 매일 장 시작 전 **증권사 잔고와 로컬 포지션을 수량·평균단가로 대조**한다. 불일치가
  정수배면 기업행위로 보고 거래를 잠근다(자동 보정하지 않는다). 사람이 확인한다.
- 손절·트레일링 기준가는 **기업행위 조정 계수**를 곱해 갱신한다. 수정주가 계수를
  제공하는 시세 소스를 쓰거나, 공시(KIND·DART)의 권리락·분할 이벤트를 받는다.
- 배당은 `cash_events` 같은 별도 테이블에 기록하고, 손익 리포트에서 **배당락 가격
  하락 + 배당 입금**을 같은 포지션에 귀속한다.

**재현 테스트**

```python
def test_split_does_not_trigger_stop():
    pos = open_position(code="005930", entry=60_000, qty=10)
    apply_corporate_action(pos, kind="split", ratio=5)      # 1:5 분할
    tick(code="005930", price=12_100)                        # 분할 후 정상 가격
    assert not stop_triggered(pos)                           # 수정 전: True
    assert pos.qty == 50 and pos.entry == 12_000
```

**검증(실데이터)** — 구간 내 기업행위 공시 목록을 뽑고, 해당 종목·날짜의 손익을
따로 본다. `queries.md` 5번.

## 2. 거래세·수수료 누락 — 체결가 × 수량 = 손익이라는 가정

**증상**

- DB 손익 합계가 증권사 실현손익보다 **항상** 크다. 차이는 매도금액에 비례한다
- 단타 전략일수록 DB와 실제의 괴리가 크다
- 사이징(Kelly 등)이 계속 커진다

**원인**

`(sell - buy) * qty`만 기록한다. 거래세는 **매도금액**에 붙고, 수수료는 양방향이다.
세율은 시장마다 다르고 해마다 바뀐다. 하드코딩한 세율은 1월 1일에 조용히 틀려진다.

편향이 **한 방향(과대보고)** 이다. 이 컬럼으로 켈리 비율을 계산하면 사이징이 스스로
커진다. 코인 부분청산 버그의 거울상이다. 저쪽은 사이징이 최소치에 붙었고, 이쪽은
최대치로 간다. 이쪽이 더 위험하다.

**수정**

- 손익은 **증권사 체결내역의 수수료·제세금 필드**를 그대로 쓴다. 직접 계산은 대조용이다.
- 직접 계산해야 하면 세율을 `(시장, 시작일, 종료일, 세율)` 테이블로 두고 **체결일
  기준으로 조회**한다. 상수로 두지 않는다.
- 수수료율은 계좌·이벤트(비대면 우대 등)마다 다르다. 체결내역의 실제 수수료와 비교해
  추정치가 맞는지 한 번은 검증한다.

**재현 테스트**

```python
def test_net_pnl_includes_tax_and_fees():
    trade = round_trip(market="KOSDAQ", buy=10_000, sell=10_100, qty=100, date="2026-03-02")
    gross = 10_000
    assert trade.net_pnl < gross                       # 수정 전: == gross
    assert trade.tax == pytest.approx(sell_amount(trade) * tax_rate("KOSDAQ", "2026-03-02"))
```

## 3. 평균단가 방식 불일치 — 이동평균 vs FIFO vs 전략별 로트

**증상**

- 전략 A 손익 + 전략 B 손익 ≠ 계좌 실현손익
- 분할매수 후 일부 매도한 거래의 손익이 증권사 앱과 다르다
- 한 전략이 다른 전략의 매수분을 팔아버린다

**원인**

국내 증권사의 잔고 평균단가는 보통 **이동평균**이다. 같은 계좌·같은 종목을 두 전략이
들면 증권사 입장에선 하나의 포지션이다. 이렇게 되면 다음이 성립하지 않는다.

- 계좌 평균단가로 전략별 손익을 계산할 수 없다
- 전략 A의 "청산" 매도가 전략 B 수량까지 줄인다 (증권사는 구분하지 않는다)

**수정**

- 전략별 손익이 필요하면 **로컬에서 로트(체결 단위)를 추적**한다. 방식(FIFO 또는
  전략별 귀속)을 정하고 문서화한다. 계좌 합계는 증권사와 맞아야 한다.
- 가능하면 **같은 종목을 두 전략이 동시에 들지 못하게** 막는다. 가장 싼 해결책이다.
- 리포트에 어느 평균단가 방식인지 적는다.

**검증** — 기간 합계로 `Σ 전략별 net == 증권사 실현손익(같은 비용 기준)`.
어긋나면 전략별 숫자를 쓰지 않는다.

## 4. 접수 ≠ 체결 — 주문 성공 응답을 포지션으로 기록

**증상**

- 로컬에는 보유 중인데 증권사 잔고에 없는 종목이 있다
- 장 마감 후 "보유 중" 포지션이 다음날 아침 사라진다
- 손익 리포트에 체결가가 아니라 **주문가**가 찍혀 있다

**원인**

주문 API의 성공 응답은 **접수 완료**다. 체결은 별도 이벤트(체결통보)나 조회로 확인해야
한다. 접수 시점에 포지션을 만들면 다음 주문이 모두 체결된 것으로 남는다.

- 지정가가 안 닿은 주문 (미체결)
- 일부만 체결된 주문 (부분체결)
- 장 마감에 자동취소된 당일 주문
- 정정·취소로 원주문이 사라지고 새 주문번호가 생긴 경우

**수정**

주문 상태 머신을 따로 둔다(`stock-trading-execution`의 주문 수명주기). 포지션은 **체결
이벤트로만** 바꾼다. 장 마감 후에는 증권사 일별 체결조회로 그날 체결을 전부 대조한다.

**재현 테스트**

```python
def test_accepted_order_is_not_a_position():
    broker.place_limit(code="000660", side="buy", qty=10, price=100_000)  # 접수 OK
    assert positions.qty("000660") == 0
    broker.emit_fill(code="000660", qty=4, price=100_000)                 # 부분체결
    assert positions.qty("000660") == 4
    broker.emit_session_close()                                           # 잔량 자동취소
    assert open_orders.count("000660") == 0 and positions.qty("000660") == 4
```

## 5. 죽은 리스크 가드 — 호출자가 없거나 빈 테이블을 읽음

코인 카탈로그 3번과 같다. 주식에서 특히 흔한 형태는 다음과 같다.

- **일손실 한도가 UTC 일자로 집계된다.** KST 09:00이 UTC 00:00이다. 장 시작 직후에
  카운터가 리셋되는 게 아니라, 계산 방식에 따라 전날 손실을 끌고 오거나 0으로 본다.
- **휴장일에 도는 롤업이 0행을 쓴다.** 다음 거래일 가드가 "어제 손실 0"을 본다.
- **"매매 중지" 플래그를 진입 경로만 확인한다.** 손절·리밸런싱 경로는 확인하지 않아서
  중지 상태에서도 주문이 나간다(이게 의도면 그렇게 문서화한다).

**행을 주입해서 통과하는 테스트는 없는 테스트보다 나쁘다.** 실전 경로(체결 이벤트 →
집계 → 가드)로 입력을 만드는 테스트를 하나는 둔다.

```bash
grep -rn "is_daily_loss_limit\|trading_halted" src/ | grep -v test   # 호출자 확인이 먼저
```

## 6. 집계 날짜 경계 — UTC 자정과 거래일

**증상**

- 일별 리포트에서 하루 매매가 두 날짜로 쪼개진다
- 월요일 리포트가 비어 있고 일요일에 매매가 찍힌다
- 휴장일(공휴일·임시휴장)에 "거래 0건, 손익 0" 행이 생겨 일평균이 희석된다

**원인**

`DATE(executed_at)`을 UTC로 자르거나, 달력일로 집계한다. 주식은 **KST 거래일** 단위가
자연스럽다. 시간외·대체거래소(NXT) 체결이 있으면 같은 거래일의 저녁 체결도 포함된다.

**수정**

- 저장은 timezone-aware(UTC)로 하고, 집계는 `AT TIME ZONE 'Asia/Seoul'`로 바꿔서 한다.
- 거래일 캘린더 테이블(KRX 휴장일)과 조인한다. 휴장일 행을 만들지 않는다.
- 자정 잡이 "오늘"을 집계하지 않게 기본값을 **직전 거래일**로 한다.

```python
def roll_up(conn, trade_date: date | None = None) -> None:
    if trade_date is None:
        # 장 마감 후·자정 이후 어느 쪽에서 돌아도 직전 거래일을 집계한다.
        trade_date = previous_trading_day(datetime.now(KST).date())
```

## 공통 교훈

1. **필드의 소비자를 감사한다.** 손익·평균단가 컬럼으로 주문 수량을 정하는 코드를
   찾는다.
2. **편향의 방향을 본다.** 비용 누락은 항상 낙관적, 기업행위 미반영은 큰 일회성
   이상치다. 진짜 노이즈는 양방향이다.
3. **잔고 대조를 매일 한다.** 수량이 맞지 않는 상태에서 나온 손익은 전부 의심한다.
4. **세율·캘린더·장 운영시간은 데이터다. 상수가 아니다.**
5. **배포 전에 새 쿼리를 실제 DB에 돌린다.** 조용한 쿼리 실패로 기능이 죽는다.
